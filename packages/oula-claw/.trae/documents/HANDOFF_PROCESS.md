# Handoff 更新流程

> 本文档定义了如何正确创建 Handoff 文档并更新最新准确文档的流程。

---

## 文档体系说明

### 三种文档类型

| 文档类型 | 文件位置 | 用途 | 更新频率 |
|---------|---------|------|---------|
| **最新准确文档** | `README.md` | 项目的唯一权威文档 | 每次功能变更 |
| **Handoff 文档** | `handoffs/XX-*.md` | 功能开发的历史记录 | 每个功能完成后 |
| **流程文档** | `HANDOFF_PROCESS.md` | 本文档，定义流程规范 | 流程变更时 |

### 文档关系

```
README.md (最新准确文档)
    ↑
    | 汇总、同步
    |
handoffs/01-*.md (历史记录)
handoffs/02-*.md
handoffs/03-*.md
...
```

## 更新流程（For AI / For Human）

### 场景 1: 完成新功能开发

**触发时机**: 完成一个功能模块的开发、测试通过、代码已提交

**执行步骤**:

```
┌─────────────────┐
│ 1. 完成功能开发  │
│ 2. 测试通过      │
│ 3. 代码已提交    │
└────────┬────────┘
         ↓
┌─────────────────────────┐
│ 4. 创建 Handoff 文档     │
│    - 命名: handoffs/    │
│      XX-feature-name.md │
│    - 记录实现细节       │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 5. 更新 README.md       │
│    - 更新项目结构       │
│    - 更新配置说明       │
│    - 更新 API 文档      │
│    - 更新最后更新时间   │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 6. 验证文档一致性       │
│    - 检查链接是否有效   │
│    - 检查代码示例       │
│    - 运行测试验证       │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 7. 提交文档变更         │
│    git add .            │
│    git commit -m        │
│    "docs: update        │
│     README and add      │
│     handoff XX"         │
└─────────────────────────┘
```

### 场景 2: 修改现有功能

**触发时机**: 修改已有功能的代码

**执行步骤**:

```
┌─────────────────┐
│ 1. 修改代码      │
│ 2. 测试通过      │
└────────┬────────┘
         ↓
┌─────────────────────────┐
│ 3. 更新 README.md       │
│    - 修改相关章节       │
│    - 更新最后更新时间   │
│    - 更新版本号（如有） │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 4. 可选：创建 Handoff   │
│    如果变更是重大修改   │
│    或需要记录决策过程   │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 5. 提交变更             │
└─────────────────────────┘
```

### 场景 3: 修复 Bug

**触发时机**: 修复 Bug 后

**执行步骤**:

```
┌─────────────────┐
│ 1. 修复 Bug      │
│ 2. 添加回归测试  │
│ 3. 测试通过      │
└────────┬────────┘
         ↓
┌─────────────────────────┐
│ 4. 评估是否更新文档     │
│    - 影响用户使用？     │
│    - 影响配置？         │
│    - 影响 API？         │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 5. 如需要，更新         │
│    README.md 相关章节   │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│ 6. 提交变更             │
└─────────────────────────┘
```

## Handoff 文档模板

创建新的 Handoff 文档时，使用以下模板：

```markdown

## 概述

简要描述这个功能是什么，解决了什么问题。

## 实现内容

### 1. [子功能/模块 1]

- 实现细节 1
- 实现细节 2
- 关键代码片段：

\`\`\`typescript
// 关键代码
\`\`\`

### 2. [子功能/模块 2]

...

## 测试

- 测试文件: `test/...`
- 测试用例: X 个
- 运行命令: `npm run test:xxx`

## 配置变更

如有新的配置项，列出：

| 变量名 | 必填 | 说明 |
|--------|------|------|
| `NEW_VAR` | 是 | 说明 |

## API 变更

如有 API 变更，列出：

### POST /new-endpoint

描述...

## 注意事项

1. 注意点 1
2. 注意点 2

## 相关文档

- [README.md](../README.md) - 最新准确文档
- [其他 Handoff](./XX-other.md)

---

创建日期: YYYY-MM-DD
文档编号: XX
```

## README.md 更新检查清单

每次更新 README.md 时，检查以下项目：

### 必须更新

- [ ] **最后更新时间**: 文档顶部的 `最后更新` 日期
- [ ] **文档版本**: 如有重大变更，更新版本号
- [ ] **项目结构**: 如有新增/删除文件，更新结构图
- [ ] **配置说明**: 如有新配置项，添加到表格
- [ ] **可用脚本**: 如有新脚本，添加到列表

### 选择性更新

- [ ] **核心模块**: 如有新模块，添加说明
- [ ] **API 端点**: 如有新接口，添加文档
- [ ] **常见问题**: 如遇到新问题，添加 Q&A
- [ ] **Handoff 历史**: 添加新的 Handoff 链接

```bash
npm test

npm run lint

# 3. 验证链接（如有工具）

```

### 手动检查

- [ ] 代码示例是否可以复制粘贴运行
- [ ] 配置文件路径是否正确
- [ ] 环境变量名称是否正确
- [ ] 脚本命令是否有效
- [ ] 版本号是否一致

## 最佳实践

### For AI

1. **始终先更新 README.md**
   - Handoff 是历史记录，README 是权威文档
   - 用户首先看 README，不是 Handoff

2. **保持文档简洁**
   - README: 只保留最新、最重要的信息
   - Handoff: 详细记录实现细节和决策过程

3. **使用相对路径**
   - 文档间链接使用相对路径，如 `./handoffs/01-xxx.md`

4. **及时更新**
   - 功能完成后立即更新文档
   - 不要累积多个功能后再更新

### For Human

1. **首先阅读 README.md**
   - 了解项目最新状态
   - 获取快速开始指南

2. **需要了解历史时查看 Handoff**
   - 某个功能为什么这样实现
   - 技术决策的背景

3. **发现文档不一致时**
   - 以 README.md 为准
   - 或询问最新状态

4. **修改代码后**
   - 遵循上述更新流程
   - 保持文档同步

## 常见问题

### Q1: 什么时候需要创建 Handoff？

**需要创建**:
- 新功能模块完成
- 重大架构变更
- 技术决策需要记录背景
- 改造/重构完成

**不需要创建**:
- Bug 修复
- 小的代码优化
- 文档 typo 修复
- 配置值调整

### Q2: README.md 和 Handoff 内容重复怎么办？

**原则**: README 精简，Handoff 详细

- README: 只保留当前状态、快速开始、核心信息
- Handoff: 详细记录实现过程、决策原因、代码细节

### Q3: 多个功能同时开发，如何更新文档？

**推荐**: 每个功能完成后立即更新

```
功能 A 完成 → 更新 README + Handoff A → 提交
功能 B 完成 → 更新 README + Handoff B → 提交
功能 C 完成 → 更新 README + Handoff C → 提交
```

**避免**: 所有功能完成后再统一更新（容易遗漏）

### Q4: 发现文档错误但代码已合并怎么办？

1. 立即修复文档
2. 单独提交文档修复
3. 如有必要，添加注释说明
